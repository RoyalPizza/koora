# C++ Standard (C-style)

Base: C-style code compiled as C++20: plain structs, free functions, `switch`-based dispatch, explicit control flow. A small allowlist of C++ features is permitted. Simplicity and readability come first. When in doubt, write it the way C would.

Why C++ at all: only for `std::string` and the containers. Strings in C mean fixed buffers and manual length tracking, a common source of bugs. Growable arrays and hash maps would otherwise be hand-written. Everything else is written as C. When a case isn't covered here, pick what keeps the code closest to C.

## Project layout
```
project-name/
    src/           all project source (.hpp/.cpp), subfolders allowed
    bin/           build output: executables, .pdb, runtime files
    obj/           intermediate build files: .obj/.o
    third-party/   vendored libraries, one folder per library
    docs/          design notes and documentation
    build.bat
    build.sh
```
- `bin/` and `obj/` are generated by the build scripts and ignored by git.
- Third-party libraries are allowed. Prefer small, single-purpose C or C++ libraries (Dear ImGui, tomlc17). Add them as git submodules in `third-party/`, one folder per library, pinned to a commit; no package managers.
- `third-party/` code is never edited in place and is exempt from this standard.

## Files
- UTF-8, LF line endings.
- Folders `kebab-case`. Files `snake_case`: `src/net/packet_queue.cpp`.
- `src/` may have subfolders to group modules. File names are unique across all of `src/`, because every object file goes into the one `obj/` folder (the module prefix already makes names unique).
- Headers `.hpp`, sources `.cpp`. A module is a `.hpp`/`.cpp` pair: `packet_queue.hpp` + `packet_queue.cpp`.
- `#pragma once` in every header. No include guards.
- Headers hold struct definitions, constants, and function declarations. Function bodies go in the `.cpp`.
- `.cpp` order, top to bottom: includes, constants, `static` data, `static` function declarations, public functions in header order, `static` function definitions. The file containing `main`/`WinMain` puts it first among the functions.

## Includes
- Order, blank line between groups: own header (in `.cpp`), project headers, third-party headers, platform headers (`<windows.h>` etc.), standard library.
- Project includes with quotes, paths from the source root: `#include "net/packet_queue.hpp"`. No `../`.
- Include what you use. Don't rely on transitive includes.

## Naming
- `PascalCase`: struct and enum types.
- `snake_case`: functions, variables, parameters, struct members.
- `CONSTANT_CASE`: constants, enum members, macros.
- Module prefix on public functions: `packet_queue_push(...)`, `packet_queue_is_full(...)`.
- No Hungarian notation. No `m_`/`g_` prefixes.
- No abbreviations except `id`, `ui`, `ptr`, `len`, loop `i`/`j`. Platform API names (`hwnd`, `msg`, `hdc`) are fine when talking to that API.

## Formatting
- 4 spaces. No tabs. Lines < 100 chars.
- Allman braces: opening brace on its own line for functions, structs, and control flow.
- Always braces on `if`/`else`/`for`/`while`, even single statements.
- `Type* ptr`, `Type& ref` (attached to the type).
- One declaration per line.
- Blank line between logical steps inside a function.

## Allowed C++
Only these. Anything not listed is not allowed.
- `std::vector`, `std::array`, `std::string`, `std::string_view`, `std::unordered_map`.
- `<algorithm>` functions on the above (`std::sort`, `std::find`, ...).
- `std::filesystem` for paths and folders. Only the overloads that take a `std::error_code`; the others throw.
- References, `const`, `constexpr`, `nullptr`, `enum class`, `static_assert`.
- Range-based `for`. Default member initializers in structs.
- Designated initializers: `Packet packet = { .id = 3, .len = 16 };`. Fields in declaration order.
- Casts are C-style: `(int)x`. Easiest to read.
- `auto` only for iterators and when the type is spelled on the same line.
- Macros. Typical uses: logging call-site capture (`LOG_WARN(...)`), typed arena pushes (`ARENA_PUSH_STRUCT`), platform/compiler switches. Constants are still `constexpr`, not `#define`.

## Not allowed
Each ban has a reason, so cases not listed can be judged the same way.
- `class`, member functions, constructors/destructors, access specifiers. Data and behavior stay separate, so any function can be read without knowing hidden object state.
- Inheritance, `virtual`, operator overloading, RTTI (`dynamic_cast`, `typeid`). They hide which code actually runs. A call should do what its name says, found by reading one function.
- Writing templates (using allowed std templates is fine). Hard to read, slow to compile, and cryptic error messages. Write the concrete type.
- Lambdas, `std::function`, function objects. Code that runs later from somewhere else breaks top-to-bottom reading. Use a named function and a `switch`.
- Exceptions. They are invisible exits from any call; errors must be visible in the return value.
- Smart pointers, `std::shared_ptr`, `std::optional`, `std::variant`, `std::any`. Ownership and lifetime are hidden behind wrappers. Ownership is explicit: the arena or pool that holds an object owns it (see Memory).
- iostreams (`std::cout`, `std::cin`, `std::fstream`). Built on operator overloading and a virtual class hierarchy. Formatting state sticks (`std::hex` stays on for later output), the `<<` chains are verbose next to a `printf` format string, and the headers are heavy to compile.
- `std::format`. Heavy templates: slow to compile, huge error messages. Use `snprintf`.
- Namespaces of our own, and `using namespace`. Module prefixes already do the job of a namespace; `using namespace` hides where a name comes from.

## Data and functions
- Data lives in plain `struct`s. Behavior lives in free functions that take the struct by pointer or reference.
- Pass by `const&` to read, by `&` or pointer to modify, by value for small types.
- Module-private functions and data: `static` in the `.cpp`.
- No mutable globals across files. A module may keep file-level `static` state when it is genuinely single-instance (the window, the audio device).
- No `static` local variables. State that outlives a call, including window procedure state, goes in file-level `static` data or a struct.
- No magic numbers: named `constexpr` constants.
- Table-driven over repeated code: when cases differ only in data, put the data in a `constexpr` array of structs and loop over it instead of writing an `if` chain or a `case` per entry.
- Share plain functions freely. Don't build generic or configurable code to merge things that are only similar; write each one out. Finished code must not break when other code changes.
- Keep functions short; one job each. Early return over nested `if`.

```cpp
struct PacketQueue
{
    std::vector<Packet> packets;
    int capacity = 0;
};

void packet_queue_init(PacketQueue& queue, int capacity)
{
    queue.packets.reserve(capacity);
    queue.capacity = capacity;
}

bool packet_queue_push(PacketQueue& queue, const Packet& packet)
{
    if ((int)queue.packets.size() >= queue.capacity)
    {
        return false;
    }

    queue.packets.push_back(packet);
    return true;
}
```

## Control flow
- Dispatch on events/messages/states with a `switch` on an `enum class` or message ID. One `case` per event; keep each `case` short and call a function if it grows.
- Every `switch` on an enum handles all members. `default` only for open sets (OS messages).
- Main loop is written out explicitly: poll input, update, draw. (Interactive programs only; a CLI tool just runs top to bottom.)
- State in variables and enums. No callbacks or event systems except where the platform requires them (`WndProc`).

```cpp
LRESULT CALLBACK window_proc(HWND hwnd, UINT msg, WPARAM wparam, LPARAM lparam)
{
    switch (msg)
    {
        case WM_SIZE:
            on_resize(LOWORD(lparam), HIWORD(lparam));
            return 0;

        case WM_DESTROY:
            PostQuitMessage(0);
            return 0;
    }

    return DefWindowProc(hwnd, msg, wparam, lparam);
}
```

## Platform
- Default: call platform APIs (Win32, POSIX) directly from the module that needs them. No wrapper layer.
- A platform layer is allowed only when the project targets more than one OS or its instructions ask for one (an engine, a Dear ImGui backend). It is one module per platform (`platform_win32.cpp`, `platform_linux.cpp`) behind a shared `platform.hpp` of free functions. Never add one speculatively.
- Text is UTF-8 inside the program. On Windows call the `W` APIs and convert at the call site. No `TCHAR`, no `A` APIs.

## Memory
- All engine and game memory comes from one block requested at startup through `platform_alloc()` (`VirtualAlloc` / `mmap`), carved into arenas grouped by lifetime:

| Arena | Holds | Reset |
| --- | --- | --- |
| Permanent | engine systems, configs, asset table | never |
| Level | entities, map data, level assets | on level change |
| Frame | temp strings, sort buffers, collision pairs | every frame |

- Allocate with `arena_push` or the `ARENA_PUSH_STRUCT` / `ARENA_PUSH_ARRAY` macros. Memory is freed only by resetting its arena. No per-object free.
- Objects with unpredictable individual lifetimes (entities, physics bodies, playing sounds) go in fixed-size pools with a free list, allocated inside an arena. Pool slots are referenced by index or generational handle, never by pointer.
- No `new`/`delete`, no `malloc`/`free` in our code.
- Size known and small (fixed-length names, small lookup tables): `std::array` on the stack or in the struct.
- `std::vector` / `std::string` only for load-time and setup work (reading files, parsing, building paths). Never allocate them per frame, and never keep them in arena or pool data.
- Third-party libraries are routed to our arenas where they allow it (`STBI_MALLOC`, miniaudio allocation callbacks, the TOML parser's allocator hooks).
- Raw pointers are non-owning. The arena or pool that holds an object owns it.

```cpp
struct Arena
{
    uint8_t* base;
    size_t size;
    size_t used;
};

void* arena_push(Arena& arena, size_t bytes, size_t align);
void arena_reset(Arena& arena);

#define ARENA_PUSH_STRUCT(arena, T) (T*)arena_push(arena, sizeof(T), alignof(T))
#define ARENA_PUSH_ARRAY(arena, T, n) (T*)arena_push(arena, sizeof(T) * (n), alignof(T))
```
- Platform handles (files, windows, GPU objects) are released by an explicit `_shutdown`/`_close` function, in reverse order of creation.
- Short-lived resources are acquired and released in the same function, release written right after the code that uses it: `BeginPaint`/`EndPaint`, `GetDC`/`ReleaseDC`, `SelectObject` then restore the old object.

## Error handling
- Functions that can fail return `bool` (or an `enum class` error code when the caller needs to tell failures apart). Results go through an out parameter.
- Check every return value. No silent failures.
- Programmer mistakes: `assert`. Stripped in release; no side effects inside `assert`.

## File I/O
- C stdio by default: `fopen`/`fread`/`fwrite`/`fclose`. Portable, needs no platform layer.
- On Windows, open with `_wfopen` and convert the UTF-8 path to wide, so non-ASCII paths work. A small wrapper that does both is fine.
- The platform API (`CreateFileW`, `open`) only when stdio can't do the job: memory-mapped files, async I/O, file locking, replacing an existing file.
- `fclose` in the same function as `fopen`, on every return path. A wrapper that only opens and returns the `FILE*` counts as `fopen`. Never store an open `FILE*` in a struct or global.

## Logging
- All logging, warnings, and errors go through the project's logging module. No direct `printf`, `std::cout`, or `OutputDebugString` outside it.
- The logging module formats with `printf`/`snprintf`. Logging functions take a format string and arguments: `log_info("health: %d", health)`.
- A command-line program's results (what scripts read) also go through the logging module, through an output function that writes to stdout. Log messages go to stderr.

## Settings
- Settings files are INI or TOML. INI is hand-parsed; TOML uses a vendored parser (tomlc17). No JSON, XML, or YAML for settings.

## Building
- No build system (no CMake, Make, MSBuild projects, Ninja, premake). Builds are plain scripts that call the native compiler directly.
- `build.bat` for Windows (MSVC `cl`). `build.sh` for Linux (`g++`) and macOS (`clang++`); pick the compiler from `uname`.
- Scripts live in the project root. Object files go to `obj/`, final output to `bin/`.
- Debug by default. Pass `release` as the first argument for an optimized build.
- C++20. Warnings as errors.
- Vendored code is compiled separately with warnings off (`/W0`, `-w`), and its headers are included as external (`/external:I` with `/external:W0`, `-isystem`), so warnings in code we don't own can't fail the build.

```bat
@echo off
setlocal enabledelayedexpansion
if not exist bin mkdir bin
if not exist obj mkdir obj
set FLAGS=/nologo /std:c++20 /W4 /WX /EHsc /Isrc /Zi /Od /Fo:obj\ /Fd:obj\
if "%1"=="release" set FLAGS=/nologo /std:c++20 /W4 /WX /EHsc /Isrc /O2 /DNDEBUG /Fo:obj\
set SOURCES=
for /r src %%f in (*.cpp) do set SOURCES=!SOURCES! "%%f"
cl %FLAGS% %SOURCES% /Fe:bin\app.exe /link user32.lib gdi32.lib
```

```sh
#!/bin/sh
set -e
mkdir -p bin obj
if [ "$(uname)" = "Darwin" ]; then CXX=clang++; else CXX=g++; fi
FLAGS="-std=c++20 -Wall -Wextra -Werror -Isrc -g -O0"
if [ "$1" = "release" ]; then FLAGS="-std=c++20 -Wall -Wextra -Werror -Isrc -O2 -DNDEBUG"; fi
for f in $(find src -name '*.cpp'); do $CXX $FLAGS -c "$f" -o "obj/$(basename "${f%.cpp}").o"; done
$CXX obj/*.o -o bin/app
```

## Testing
- No test frameworks (GoogleTest, Catch2). Tests, if a project has them, are plain functions that `assert`, or that report each failure and exit non-zero.

## Comments
- Short comment above each function in the header saying what it does and what it returns on failure.
- Comments explain why, not what.
- No commented-out code.
